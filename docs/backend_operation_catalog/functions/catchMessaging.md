| `adminSendCatchWhatsappReply` (`purpose: supportConversation`) | Callable | Admin Support reply box on a WhatsApp conversation | `supportConversations/{id}`, `.../messages/{cwsupport_…}`, `adminAuditLogs`; reads `catchWhatsappEndpointStops` | Sends one free-form text from Catch's number to the conversation's WhatsApp sender. Support roles, App Check, 30 a minute per staff member and 5 a minute per conversation. Only inside WhatsApp's 24-hour window after the person's last message (by WhatsApp's timestamp, a minute's margin), never after STOP, and only while `CATCH_WHATSAPP_REPLIES_ENABLED` is on; outside the window it refuses (the host lead follow-up template below is the one message staff can send then). The message is created as `sending` before WhatsApp is called and keyed on the client request id, so a retry returns the first outcome; a WhatsApp refusal marks it `failed`, a lost answer `unknown`, and neither is resent. The WhatsApp message id is saved, and status receipts move it to sent, delivered, read or failed. The claim and the outcome are audited, without the text. Uses the trial's pinned `CATCH_WHATSAPP_REPLY_CREDENTIAL_VERSION`/`_GRAPH_VERSION`. `adminGetSupportConversation` reports the reply mode, whether sending is possible now, why not, and when the window closes. |
| `adminSendCatchWhatsappReply` (`purpose: hostLeadFollowUp`) | Callable | Admin Inbox "Send follow-up" on an open host lead | `supportConversations/{id}` (created when they have none), `.../messages/{cwfollowup_…}`, `salesInboundIntents/{id}.followUpWhatsapp`, `adminAuditLogs`; reads `catchWhatsappEndpointStops` | Sends the approved `host_lead_follow_up` template (language `en`, Marketing, `{{1}}` the first word of the lead's name or "there", static quick replies "Book a walkthrough" and "Not now") to the lead's phone. Admin, owner and support roles, App Check, 30 a minute per staff member and 5 a minute per lead. Only for website leads other than `referral` and `city_alerts`, and Meta lead-form leads, still awaiting review; only while `CATCH_WHATSAPP_REPLIES_ENABLED` is on; never after STOP; refused while the person's last message is under 24 hours old (staff reply in Support instead); at most one per WhatsApp number in any 7 days, counting every attempt WhatsApp did not refuse. Keyed on the client request id and created as `sending` before WhatsApp is called, so a retry returns the first outcome; refused marks it `failed`, a lost answer `unknown`, neither resent. Uses the reply sender's pinned credential and Graph version; Catch's token cannot read the template list, so the template's name, language and variable live in `catchMessaging/catchTemplates.ts`. |
| `onCatchWhatsappWebhookEventCreated` (Support) | Firestore trigger on `catchWhatsappWebhookEvents` create | Backend | `supportConversations/{id}`, `.../messages`, `catchWhatsappAutoReplies` | Inbound messages that are not nominations land in Support. A photo, voice note, video, document, sticker, location, contact or button/list reply is kept as a placeholder ("[photo]", "[voice note]", "[document: name]", the button's label); the media is never downloaded, and such messages stay blocked ingress, so they are never parsed as nominations, STOP or trial input. Reactions and system notices are skipped. A support message that is the person's first, or their first after 24 hours of silence, gets "Thanks. Status receipts for Support replies update their message. |
