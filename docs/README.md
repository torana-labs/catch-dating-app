# Docs Index

This folder should contain durable source-of-truth documents, not every session
report or temporary audit note. When a cleanup pass discovers new guidance, move
the durable decision into the relevant source-of-truth doc and delete the stale
or duplicated note once it has served its purpose.

## Read Policy

Use this index to find the durable owner for a topic, then read only the
relevant section unless the task requires a full historical audit. Source
frontmatter and this index own documentation metadata; there is no parallel
document catalog.

## Documentation Hygiene

- Prefer updating an existing source-of-truth document over creating a new one.
- Create a new document only when it has a distinct durable owner, audience, and
  update path.
- Do not keep duplicate or conflicting trackers for the same work. If two docs
  disagree, reconcile them and leave one clear owner.
- Session reports, email drafts, and one-off implementation summaries should not
  live here after their durable decisions or backlog items have been migrated.
- Date-stamped audits are snapshots. Re-verify counts, statuses, and code paths
  before treating them as current.
- Treat semantic document versions as authored contract metadata, not an edit
  counter. `node tool/docs/check_doc_metadata.mjs --base <base>` validates
  source metadata and retirement directly from Git without generating a
  tracked catalog or integration commit.

## Feature Answers And Generated References

Keep a short feature explanation beside its owning code: purpose, user jobs,
boundaries, important behavior, examples, and links to deeper contracts. Use this
folder for cross-feature architecture, product policy, decisions, and runbooks.
Keep only unresolved delivery work in `plans/`; remove completed handoffs after
moving their durable content to an owner.

Audience is the first source-linked guide. Its questions, aliases, authored
answers, explicit source dependencies, and named test examples live in the
existing Host responsibility contract. Its README and schema-derived limits are
generated. Read the guide before opening all of the implementation:

```sh
node tool/design/build_host_feature_responsibilities.mjs --explain audience
node tool/design/build_host_feature_responsibilities.mjs --explain audience --question membership --json
node tool/design/build_host_feature_responsibilities.mjs --affected audience --base origin/main --json
node tool/docs/check_doc_metadata.mjs --inventory --query audience
node tool/docs/check_doc_metadata.mjs --base origin/main
```

The inventory is disposable stdout, derived from repository Markdown; it lists
metadata, headings, size, and literal document references. It is not another
maintained catalog. Prefer it and focused searches to repeatedly reading every
document.

Generated schema facts and broken source/example references are checked
mechanically. Changed declared source paths flag specific answers for review;
that advice does not prove prose is correct, follow every transitive import, or
prove that a named test passes. Review the meaning, run the selected checks, and
change the explanation only when needed. Do not mark an answer reviewed merely
because its generated bytes match.

When a recurring question is missing, add it to the owning feature guide with
its source references and an example. The Audience retrieval test protects the
initial recurring question set; add equivalent focused coverage as other
feature guides adopt the pattern. Reuse existing contracts and the Harness
impact graph; do not create a parallel dependency graph or tracked run history.

## Document Retirement

Treat retirement as an ownership change: preserve unique product intent,
architecture decisions, operational procedures, and unresolved requirements in
their existing durable owners before removing a completed plan. Current feature
contracts replace route/state/action inventories; they do not replace product
policy, rationale, copy, or release procedures. Git retains completed work and
historical evidence.

Source frontmatter owns governed-document identity, version, date, owner, and
status. The metadata check rejects malformed metadata, duplicate identities,
identity swaps, and version decreases. Against a base revision, it also rejects
surviving literal Markdown links or code-span references to Markdown removed or
renamed in that change. It includes ungoverned Markdown and ignores fenced
examples; code consumers, dynamic references, and external links still need
focused review. This is reference protection, not automatic permission to delete.

## Before Adding A New Doc

1. Check whether the information belongs in one of the documents above.
2. If it is a temporary pass report, add only durable findings to the active
   tracker or architecture doc.
3. If a new durable document is still necessary, add it to this index with its
   owner area and update path.
4. Delete or mark any superseded document in the same pass so the docs folder
   does not accumulate stale sources of truth.
